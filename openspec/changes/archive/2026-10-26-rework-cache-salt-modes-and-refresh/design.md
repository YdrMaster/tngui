# Design

## Context

缓存盐现有实现是一条从前端到反代的窄链路：`frontend/src/cacheSaltConfig.ts` 持有配置，`useCacheSaltConfig` 通过 `configure_cache_salt` 命令下发，`tngui-core/src/cache_salt.rs` 里的 `CacheSaltHandle` 做惰性轮换，`proxy.rs` 在解析出有效模型后调用 `inject_cache_salt` 改写请求体。盐值只在进程内存里，只进请求体。

这轮改动要把模式语义、刷新渠道和前端回填一起换掉，几处约束会同时咬住设计：

- 只有反代看得到请求量，也只有在反代里做轮换才不会引入后台任务，所以盐值的唯一持有者必须在 Rust 侧。
- GUI 现在要显示"当前实际使用的盐"，这是一条新的、从前端往未知方向要数据的通道，而盐值又不许进诊断快照、日志和设置缓存。
- 输入框焦点只压住显示回填，压不住后台换盐，于是"文本框内容"和"实际使用的盐"会短暂分叉，失焦是唯一能对齐二者的时机。
- 单测、前端组件、反代调用点都按旧的三态加覆盖开关写好了，替换时要保证既有不变量（最小侵入改写、快照不含盐、忽略模式不动 body）不被打松。

## Goals / Non-Goals

**Goals:**

- 用一个模式枚举表达"忽略 / 添加 / 覆盖"，把原来的覆盖开关收进枚举。
- 让定时、定量、直接改三条渠道共用一个盐值状态，任一触发就换盐并同时重置两条记录。
- 给前端一条只读的当前盐通道，够它做回填，又不让它顺手把计数或轮换推着走。
- 旧设置缓存不做破坏性迁移也能读起来。

**Non-Goals:**

- 不引入后台定时器线程。轮换仍然按请求惰性判定，没人发请求就不会换盐。
- 不把盐值写进设置缓存、`tng-runtime.json`、日志或诊断快照。
- 不改动 `ProxyDiagnosticsSnapshot` 的字段构成。
- 不动 tng 配置模型与 tng 进程生命周期。

## Decisions

### 模式枚举与注入决定

核心侧的 `CacheSaltMode` 换成 `Ignore / Add / Overwrite`。`CacheSaltPolicy` 去掉 `fixed_value` 与 `overwrite`，改为：模式、定时刷新的开关与周期、定量刷新的开关与阈值。

`CacheSaltHandle::current()` 仍然返回 `Option<SaltDecision>`，把模式折进去：

- 忽略 → `None`。调用点直接跳过注入，`cache_salt` 字段既不读也不写，body 连解析都不必再碰。这与"关闭"不同：关闭曾经也是 `None`，但现在忽略是唯一的"不介入"语义，且下方控件全部隐藏，前端不会给人留下"配了盐但没生效"的错觉。
- 添加 → `Some(SaltDecision { value, overwrite: false })`。
- 覆盖 → `Some(SaltDecision { value, overwrite: true })`。

`inject_cache_salt(body, object, decision)` 的签名不用动，覆盖/插入的分支照旧走：覆盖且有 `cache_salt` 时走 `find_top_level_member_value` 就地替换，其余情况在首个 `{` 后插入。这样"请求体改写最小侵入"这条不变量原封不动，只是它现在多了一条合法路径。

### 轮换与计数都在同一个写锁里

`SaltInner` 增加两个记录：`requests_since_reset`（自上次刷新起已计数的请求数）和既有的 `generated_at`。`current_at(now)` 每次被反代调用时按顺序做三件事：

1. 若定时开关打开且 `now - generated_at` 到点，换新盐，把 `generated_at` 设为 `now`，计数清零。
2. 否则若定量开关打开且 `requests_since_reset >= threshold`，换新盐，同样把两条记录一起清零。
3. 把这个请求计入 `requests_since_reset`。

计数与轮换复用同一个 `RwLock` 写锁，请求在注入点串行进出。阈值语义由此自然落在用户的例子上：配置 50 时，第 50 个请求把计数推到 50，第 51 个请求在发出前先撞上 `>= 50` 触发换盐。定时先到就先按定时走，计数被清零，下次再攒。

备选方案是 `AtomicU64` 计数加 `Instant`，省掉写锁；代价是"定时判定 + 计数判定 + 换值"无法成为一次原子操作，会出现两个请求同时触发轮换、或者定时刚清零计数又被并发请求读到旧值的缝隙。这里请求量不大，锁的代价远小于正确性风险。

计数只统计走到注入点的请求，也就是三类受支持端点、`model` 合法、未超 10 MiB 的那些。被 fail-closed 拒掉或走非推理端点的请求不计数——它们本来就不会带盐出去，计入反而会让阈值提前。

### 前端读盐走只读命令，轮换仍归反代

新增两条命令和一个读接口：

- `set_cache_salt_value(value)`：把当前盐换成给定值，并重置定时与计数。这是"直接改盐值"这条渠道的入口。
- `current_cache_salt()`：返回当前实际使用的盐；忽略模式返回 `None`。
- `CacheSaltHandle` 上的只读访问器（`peek_current`）：不加锁改状态、不判定轮换、不计数，只把当前值抄一份出来。

把读和写分开是必须的：如果让 GUI 轮询去调 `current()`，每次回填都会把 `requests_since_reset` 加一，定量刷新会被界面可见与否影响。所以前端能调到的读路径只能是纯读。

配置本身仍走 `configure_cache_salt`，但入参只剩模式与两条刷新参数（开关 + 数值）。改参数只重置基线记录、不换盐，与"直接改盐值"区分开。

### 前端回填：焦点门控 + 失焦对账

设置页持有两个东西：共享的盐配置，以及输入框自己的草稿 `saltDraft`。

- 输入框未聚焦时，一个 watcher 把 `saltDraft` 跟着"当前盐"走。当前盐来自设置页可见期间的轮询（`current_cache_salt`），间隔取秒级即可，反正是惰性轮换，只在有请求流过时才变。
- 输入框聚焦期间，watcher 不回写草稿，但轮询继续跑——后台换盐照换，只是不显示。
- 失焦时调一次 `current_cache_salt` 拿权威值再比对：草稿非空且与权威值不同，就当作一次直接刷新，调 `set_cache_salt_value(草稿)`；草稿为空或与权威值相同，就把草稿重置为权威值，什么都不改。
- "生成随机值"按钮复用 `randomSaltValue()` 生成一个 128 位十六进制串，填进草稿并立刻按直接刷新提交。这条路径不额外开命令：它和手输就是同一件事，只是值由程序给。

备选方案是让 Rust 在每次轮换时推 Tauri 事件给前端。省掉轮询，但要把 Tauri 的 emitter 塞进 `tngui-core`（或者给 `CacheSaltHandle` 挂回调），核心库就得知道上层 GUI 的存在。轮询多花几次 IPC，换来核心库保持干净，这个交换更划算。失焦对账本来就是一次显式命令调用，不靠事件也不会错。

### 设置缓存字段

`tng.cacheSalt` 改为只存配置：`{ mode, timerEnabled, refreshMinutes, countEnabled, countThreshold }`，不再有值字段。`schemaVersion` 保持 1，`restoredCacheSalt` 逐字段校验、逐字段回落：模式只认新枚举，其余字符串（包括旧的 `off`/`fixed`/`auto`）一律回落默认"添加"；两条开关与两个数值各自独立回落。不做旧值到新模式的语义映射——旧缓存本来就允许被当作非法处理，为了让 `off → ignore`、`overwrite: true → overwrite` 这类映射准确，还得读已经废弃的字段，收益不成比例。

## Risks / Trade-offs

- [倍率歧义] "定量 50 是第 50 个还是第 51 个请求换盐" 容易读错 → 规格里写死"已转发数达到阈值后的下一个请求"，并把用户的 30 分钟 + 50 请求的例子直接写成一个场景。核心侧单测按同一例子钉住边界。
- [轮询延迟] 设置页不动时后台换了盐，界面最多晚一个轮询周期才回填 → 周期取秒级；失焦时总是重新拉一次权威值，用户手动操作的那条路径不依赖轮询。
- [poll 误触发计数] 读接口若复用了 `current()`，轮询会把定量计数推快 → 读接口单独走只读访问器；加一条单测断言"连续读不改变当前盐，也不推进计数"。
- [写锁在高并发下成为热点] 每个请求都要进一次写锁 → 请求量级远低于锁的吞吐，先按正确性优先；若日后成为瓶颈，再考虑把"是否到点"的判断拆成读锁快路径。
- [旧缓存语义静默变化] 老用户的"关闭"会恢复成"添加"，等于开始加盐 → `schemaVersion` 不升版是有意的兼容选择，落地时在提交说明里点明；若不能接受，再单独开改动做显式迁移。

## Migration Plan

1. 核心侧先换枚举与策略结构，同步更新 `cache_salt.rs` 与 `proxy.rs` 的单测，保证"覆盖就地替换""忽略不动 body"仍有断言。
2. 换 `configure_cache_salt` 入参，新增 `set_cache_salt_value` 与 `current_cache_salt` 两条命令，前端按新命令接入。
3. 前端换配置类型、控件与失焦对账逻辑，同步更新组件测试与设置缓存测试。
4. 回滚就是整体回退这次改动；设置缓存字段与旧版本不互认，但两侧都按"缺失或非法即回落默认"处理，不会让 GUI 起不来。
